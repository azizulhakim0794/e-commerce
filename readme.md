# MyShop

## Project Description

MyShop is a full-stack e-commerce application built with Django on the backend and React with TypeScript on the frontend. The application lets visitors browse products, view product details, create an account, sign in, add products to a cart, and place orders. Authenticated users can also review their previous orders. Django exposes JSON endpoints for the business operations, and the React application consumes those endpoints through Axios and presents the shopping experience in the browser.

The project is intentionally divided into two applications. The `backend` directory contains the Django project, database models, authentication, API views, migrations, and administration configuration. The `frontend` directory contains the Vite setup, React entry point, routes, reusable components, pages, client-side state, API helpers, and TypeScript types. SQLite is used during development so the project can be run without setting up a separate database server.

## Backend Files

`backend/manage.py` is Django's command-line entry point. It is used to run the development server, apply migrations, create administrative users, run tests, and execute other Django management commands. `backend/backend/settings.py` is the central configuration file: it registers the four application areas, Django REST Framework, and CORS support; selects SQLite; declares the custom user model; configures sessions and CSRF; and allows the local Vite server to make credentialed requests. `backend/backend/urls.py` is the top-level URL router. It exposes the Django admin and mounts the authentication, product, cart, and order URLs under the API paths used by the frontend. `backend/backend/asgi.py` and `backend/backend/wsgi.py` are the ASGI and WSGI deployment entry points generated by Django. They allow the same project to run with modern asynchronous-compatible servers or traditional WSGI servers. `backend/backend/__init__.py` marks the Django project directory as a Python package.

`backend/backend.md` contains project notes about the backend and authentication. It is useful as supplementary documentation, although the active implementation uses Django session cookies; any older JWT wording in that file should be treated as historical rather than as the current authentication design. `backend/db.sqlite3` is the development database containing the local tables and data. It is convenient for development, but a production deployment would normally use environment-managed secrets and a production database instead of committing development defaults.

### Accounts App

`backend/accounts/models.py` defines the custom `User` model. It extends Django's `AbstractUser`, preserving Django's password hashing, permissions, groups, and admin integration while replacing the default integer primary key with a UUID. `backend/accounts/views.py` implements registration, login, logout, and the current-user endpoint. Login accepts either an email address or username, and successful authentication creates a normal Django session. The views return JSON data manually so the frontend receives the fields it needs without exposing the password.

`backend/accounts/urls.py` maps the account endpoints to the view functions, including registration, login, logout, and `/me/` for restoring the logged-in user after a page refresh. `backend/accounts/admin.py` registers the custom user with Django's admin site, while `backend/accounts/apps.py` contains the app configuration. `backend/accounts/tests.py` covers the most important authentication behavior: registration, email login, session persistence, anonymous access to `/me/`, and logout. `backend/accounts/__init__.py` is the package marker. `backend/accounts/migrations/0001_initial.py` is Django's generated initial migration for creating the custom user table and its inherited authentication fields.

### Products App

`backend/products/models.py` defines the catalog's `Product` model. A product has a name, description, decimal price, stock quantity, image URL, and creation and update timestamps. Decimal prices are used instead of floating-point numbers because currency calculations should not depend on binary floating-point rounding. `backend/products/views.py` provides public product-list and product-detail GET endpoints and converts model instances into JSON responses. `backend/products/urls.py` connects those views to the product collection and individual-product routes. `backend/products/admin.py` makes products manageable through Django admin, and `backend/products/apps.py` provides the application configuration.

The product migration files record how the catalog schema evolved. `0001_initial.py` creates the original product table; `0002_rename_product_name_product_name.py` records the field rename that produced the current `name` field; `0003_alter_product_name_alter_product_price.py` changes the name and price field definitions, including explicit decimal precision; and `0004_product_created_at_product_updated_at.py` adds timestamps. `backend/products/migrations/__init__.py` marks the migration directory as a package. `backend/products/tests.py` is the product test module, but it is currently empty and is a natural place to add API and stock-related coverage.

### Cart App

`backend/cart/models.py` defines the relationship between a user's cart, its cart items, and products. A user has one cart, and the database constraint prevents the same product from appearing as duplicate rows in that cart. `backend/cart/views.py` exposes authenticated cart operations for reading the cart, adding a product, and deleting a product. It validates product existence, quantity, and stock; when a product is added again, the existing item's quantity is increased rather than creating a second item.

`backend/cart/serialized.py` is a small manual serialization layer for cart responses. It includes product summaries, item quantities, item subtotals, total item counts, total quantities, and the cart subtotal so the frontend does not have to reconstruct those values. `backend/cart/urls.py` maps the cart collection and product-specific deletion route. It also contains older commented-out endpoint code that documents an earlier approach but is not active. `backend/cart/admin.py` registers carts and cart items, and `backend/cart/apps.py` contains the app configuration. `backend/cart/tests.py` is currently an empty test module. `backend/cart/migrations/0001_initial.py` creates the cart and cart-item tables and their uniqueness constraint, while `0002_remove_cart_created_at_remove_cart_updated_at.py` records the later removal of timestamps from the cart model. Both `backend/cart/__init__.py` and `backend/cart/migrations/__init__.py` are package markers.

### Orders App

`backend/orders/models.py` defines orders and order items, including order status, delivery information, totals, and monetary values. Order items store snapshots of the product name, price, and image rather than relying only on the current product row. This is a deliberate choice: if a product is renamed, repriced, or removed later, an old order should still describe what the customer purchased at checkout. `backend/orders/views.py` lists the authenticated user's orders, checks out the current cart, and supports a direct one-product purchase. Checkout validates stock, creates order items, decreases inventory, and clears the cart inside a database transaction. The direct-purchase path also uses transactional stock locking to reduce the chance of overselling when requests happen concurrently.

`backend/orders/serialized.py` converts orders and their item snapshots into the nested JSON shape expected by the frontend. `backend/orders/urls.py` maps the order-history, cart-checkout, and direct-purchase endpoints. `backend/orders/admin.py` registers orders and order items for administration, and `backend/orders/apps.py` provides the app configuration. `backend/orders/tests.py` is currently empty. `backend/orders/migrations/0001_initial.py` creates the order and order-item tables, while `backend/orders/__init__.py` and `backend/orders/migrations/__init__.py` mark their directories as Python packages.

## Frontend Files

`frontend/package.json` defines the Vite development, build, lint, and preview commands and declares the application's dependencies. React and React DOM render the interface, React Router handles navigation, Axios communicates with Django, Zustand stores authentication state, and Bootstrap with React Bootstrap supplies responsive layout and UI components. `frontend/package-lock.json` locks the exact npm dependency tree so installations are repeatable. `frontend/index.html` is Vite's HTML shell and provides the DOM element into which React mounts. `frontend/vite.config.ts` enables the React plugin and proxies `/api` requests to Django at `127.0.0.1:8000`, which keeps browser API calls simple during local development. `frontend/eslint.config.js` configures JavaScript, TypeScript, React Hooks, and React Refresh linting. `frontend/tsconfig.json` connects the browser and Node configurations; `frontend/tsconfig.app.json` applies strict checks and unused-code checks to application code; and `frontend/tsconfig.node.json` configures TypeScript for Vite's configuration files.

`frontend/src/main.tsx` is the frontend entry point. It loads Bootstrap styles and scripts, asks the authentication store to restore the current session through `/auth/me`, and then renders the router inside React Strict Mode. `frontend/src/App.tsx` is an unused placeholder component retained from the initial Vite setup. `frontend/src/layout/MainLayout.tsx` provides the shared page frame, placing the navbar above a Bootstrap container. `frontend/src/components/Navbar.tsx` changes its links based on authentication state, displays the signed-in user's name, and provides logout behavior.

### Routing, State, and API Code

`frontend/src/router/router.tsx` defines the public routes for the home page, authentication pages, about page, and product details. It places the cart, checkout, and order-history pages behind `ProtectedRoute.tsx`. `frontend/src/router/ProtectedRoute.tsx` shows a loading state while authentication is being restored, redirects anonymous users to login, and renders protected children through React Router's `Outlet`.

`frontend/src/stores/auth.store.ts` is the Zustand store for global authentication state. It holds the current user, initializes that user from Django's `/auth/me/` endpoint, and clears the user on logout. The store does not put JWTs or user credentials in localStorage because Django's session cookie is the source of truth. `frontend/src/helper/api/index.ts` creates the shared Axios client. It sends cookies with `withCredentials`, reads Django's CSRF cookie, attaches the `X-CSRFToken` header to unsafe requests, and provides reusable GET, POST, PUT, DELETE, and upload helpers.

`frontend/src/helper/service/auth.service.ts` contains the authentication-specific API calls for login, registration, logout, and current-user lookup, along with consistent extraction of authentication errors. `frontend/src/helper/service/product.service.ts` contains API calls for products, carts, and orders, keeping HTTP details out of the page components. `frontend/src/hooks/useApi.ts` is a generic request-state hook that tracks data, loading, errors, and success and normalizes the result shape used by consumers. `frontend/src/config/env.ts` reads the optional `VITE_API_BASE_URL` environment setting so the API base can change between environments. `frontend/src/type/auth.ts` and `frontend/src/type/product.ts` define the TypeScript contracts for users, authentication responses, products, carts, orders, and related API data. `frontend/src/data/product.ts` contains static sample products from an earlier development stage; the home page now loads its catalog from Django, so this file is currently unused.

### Page Components

`frontend/src/pages/home/Home.tsx` requests products from the backend and renders the storefront home page, including the hero area, product grid, feature sections, navigation links, and footer. `frontend/src/pages/authentication/Login.tsx` provides the email-and-password login form, displays API errors, shows loading feedback, updates the Zustand store, and redirects successful users to the home page. `frontend/src/pages/authentication/Register.tsx` handles account creation and performs client-side checks such as password confirmation, minimum password length, and acceptance of the terms checkbox before submitting to Django.

`frontend/src/pages/aboutUs/AboutUs.tsx` is the static about page describing the store's values and shopping workflow. `frontend/src/pages/product/ProductCard.tsx` is the reusable catalog card that displays an image, description, price, stock badge, and link to details. `frontend/src/pages/product/ProductDetials.tsx` loads products, selects the product identified by the route, displays stock-aware quantity controls, and supports both adding to the cart and buying immediately. Its filename contains the existing `Detials` spelling, but the component remains part of the active product-details route.

`frontend/src/pages/cart/Cart.tsx` loads the authenticated cart, displays its items and totals, supports item removal, and opens the order confirmation modal. `frontend/src/pages/modals/OrderConfirmModal.tsx` provides the shipping form and decides whether to call cart checkout or direct one-product checkout depending on the data it receives. `frontend/src/pages/product/ProductOrder.tsx` loads order history and displays status badges, delivery information, item snapshots, totals, and an empty state. `frontend/src/pages/product/ProductCheckout.tsx` is currently a placeholder that only renders `This is ProductCheckout`, and `frontend/src/pages/product/Product.tsx` is another unused placeholder retained from an earlier structure.

The `frontend/src/assets` directory contains frontend assets available to Vite. `frontend/README.md` is the documentation generated by the original Vite template and mainly describes generic frontend commands rather than MyShop-specific behavior. `frontend/.gitignore` excludes generated and local-only frontend files. These files support the development toolchain rather than implementing store behavior directly.

## Design Decisions

The most important design decision is session-based authentication. Django already provides secure password handling, session management, logout, and permission integration, so the project uses Django's `SessionAuthentication` instead of adding JWT creation, refresh, expiration, and client-side token storage. Axios sends credentials with each request, and the frontend calls `/auth/me/` on startup to synchronize its Zustand state after a refresh. Because the frontend and backend run on different local origins, CORS is configured to allow credentials, and CSRF protection is handled through Django's CSRF cookie plus the `X-CSRFToken` header added by the Axios client. This keeps authentication state owned by the backend and avoids exposing a bearer token to JavaScript storage.

The API uses small manual serialization functions in the accounts, cart, and orders areas instead of introducing a full serializer layer for every model. That choice keeps the response shapes explicit and makes it easy to include calculated values such as cart subtotals and order item snapshots. The tradeoff is that those functions must be maintained manually when models or response contracts change. The catalog is public because browsing products should not require an account, while carts and orders require an authenticated session because they contain user-specific state.

The cart and checkout models separate a reusable cart from permanent orders. Database uniqueness protects a cart from duplicate product rows, and transactions protect checkout operations while stock is checked and changed. Order item snapshots preserve the historical meaning of a purchase even when the catalog changes later. React uses local component state for page-specific data and Zustand only for authentication because product, cart, and order data does not need to be shared globally across every page. Bootstrap was chosen for responsive layout and established form and navigation components, allowing the project to concentrate on the store workflow instead of building a complete design system from scratch.

## Current Status and Limitations

This is a working development project rather than a production deployment. The default settings still use `DEBUG = True`, a development secret key, SQLite, and localhost CORS origins, so those values must be moved to environment-specific configuration before deployment. Product, cart, and order test modules also need broader coverage. The frontend still contains placeholder pages, some links such as forgot-password and terms do not have implemented routes, and the product-details page currently loads the product collection and searches locally instead of calling the backend detail endpoint. These are known areas for future refinement rather than hidden behavior.
